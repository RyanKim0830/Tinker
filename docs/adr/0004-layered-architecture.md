# ADR-0004: 레이어드 아키텍처 (프레젠테이션 → 비즈니스 → 인프라)

- **Status**: Accepted — 사용자 확정 (작업 지시서의 '확정된 결정')
- **Date**: 2026-10-03

## Context

책임이 섞이면 나중에 스트리밍(SSE)·툴 콜링을 얹을 때 어디를 고칠지 알기 어렵다. 한편 개인 사용 시스템이라 확장성·멀티테넌시·고가용성 설계는 기본으로 깔지 않는다.

## Decision

세 레이어로 나누고 **의존은 위에서 아래로만, 레이어 건너뛰기를 금지**한다.
- 프레젠테이션(router): 요청 검증·변환, 응답/예외를 외부 형식으로 포장. 비즈니스 로직 금지.
- 비즈니스(service): 규칙 판단과 처리. HTTP·외부 통신 방식을 몰라야 한다.
- 인프라(client): 외부 통신, 형식 변환, 연결 정보 관리. 비즈니스 판단 금지. 외부 에러는 내부 예외로 바꿔서 올린다.

예외도 한 칸씩만 올라간다 (httpx → LLM* → Chat* → HTTP 상태). 자세한 규칙·그림은 [architecture.md](../architecture.md).

## Considered Options

- 레이어 없는 단일 파일: 가장 단순하지만 책임이 섞인다
- 헥사고날/Protocol(포트·어댑터): 이번 범위에서 제외(지시서) → open-items O-09

## Consequences

- 레이어마다 한 칸 아래를 가짜로 바꿔 독립 테스트할 수 있다 ([testing.md](../testing.md)).
- 예외 변환 코드가 레이어마다 생긴다(라우터가 llm 예외를 몰라도 되게 하려고 서비스 예외를 따로 둠 → O-05).

## Revisit when

레이어 경계가 오히려 개발을 막거나, 인터페이스(Protocol)로 교체 가능성이 실제로 필요해질 때.
